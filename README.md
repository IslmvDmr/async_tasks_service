# Async Task Service

Небольшой сервис для постановки асинхронных задач в очередь и отслеживания их статуса через HTTP API.

## Что делает сервис

Сервис принимает задачу через FastAPI, сохраняет её в базе данных, выставляет статус `PENDING` и публикует сообщение в RabbitMQ для последующей обработки воркером.

- Воркер читает сообщения из очереди, запускает обработку задачи в отдельном процессе и обновляет статус задачи на `IN_PROGRESS`, `COMPLETED`, `FAILED` или `CANCELLED`.
- Каждый воркер запускает задачу в отдельном процессе, число процессов ограничено семафором. UID задачи и PID сохраняется отдельный словарь, в случае отмены процесс обработки прервется.
- Статус отмены мониторится через каждые n-секунд (настраивается индивидуально)
- Сервис поддерживает приоритезацию задач через RabbitMQ. Очередь создаётся с параметром `x-max-priority`, который задаётся через `TASK_QUEUE_MAX_PRIORITY` (по умолчанию `10`). 
Это позволяет RabbitMQ выдавать задачи с более высоким приоритетом раньше задач с более низким приоритетом. При этом приоритет не влияет на уже выполняющиеся задачи — он определяет только порядок обработки задач, ожидающих в очереди.
Внутреннее отображение приоритетов:
- `LOW` -> `1`
- `MEDIUM` -> `5`
- `HIGH` -> `10`


## Основные компоненты

- **FastAPI API** — точка входа приложения, подключает роуты задач и поднимает HTTP-сервис с названием из конфигурации.
- **Task router** — CRUD-подобные endpoints для создания, получения, отмены и просмотра статуса задач.
- **Task service** — слой бизнес-логики между API, репозиторием и publisher.
- **Task repository** — работа с таблицей `tasks`: создание, получение, листинг, отмена и выбор старых задач.
- **RabbitMQ publisher** — отправка задачи в очередь с приоритетом на основе `TaskPriority`.
- **Worker** — consumer очереди, supervisor и runner для фоновой обработки задач.


## Конфигурация приложения

Все настройки задаются через переменные окружения.

- `APP_NAME` (str, default: `"Task Service"`) — название сервиса
- `APP_HOST` (str, default: `"0.0.0.0"`) — хост для запуска приложения
- `APP_PORT` (int, default: `8000`) — порт для доступа к приложению
- `DEBUG` (bool, default: `True`) — режим отладки (подробные логи, автоперезагрузка)
- `DATABASE_URL` (str, **обязательная**) — URL подключения к базе данных  
  *Пример:* `postgresql://user:pass@localhost:5432/db`
- `AMQP_URL` (str, **обязательная**) — URL подключения к брокеру сообщений (RabbitMQ)  
  *Пример:* `amqp://guest:guest@localhost:5672/`
- `TASK_QUEUE_NAME` (str, default: `"tasks"`) — имя очереди задач в брокере
- `TASK_QUEUE_MAX_PRIORITY` (int, default: `10`) — максимальный приоритет задачи (от `0` до указанного значения)
- `MAX_CONCURRENT_PROCESSES` (int, default: `1`) — максимальное количество одновременно выполняемых процессов
- `TIME_TO_WAIT_TASK` (int, default: `10`) — время ожидания задачи (в секундах)

### Пример файла `.env`

```env
APP_NAME=Task Service
APP_HOST=0.0.0.0
APP_PORT=8000
DEBUG=False
DATABASE_URL=postgresql://user:password@localhost:5432/tasks
AMQP_URL=amqp://guest:guest@localhost:5672/
TASK_QUEUE_NAME=tasks
TASK_QUEUE_MAX_PRIORITY=10
MAX_CONCURRENT_PROCESSES=4
TIME_TO_WAIT_TASK=30
```

## Запуск

### Локально
Для FastAPI
```bash
python main.py
```
Для Consumer
```bash
python app/services/consumer.py
```

Приложение поднимает FastAPI и слушает порт `8000` в `__main__`-режиме.

### Через Docker Compose

В `docker-compose.yaml` уже описаны сервисы:

- `postgresql`
- `rabbitmq`
- `fastapi`
- `worker`

Пример запуска:

```bash
docker compose up --build
```

После старта API будет доступно на `http://localhost:8000`, RabbitMQ Management UI — на `http://localhost:15672`.

## Поток обработки задачи

1. Клиент создаёт задачу через API.
2. Сервис сохраняет её в БД со статусом `PENDING`.
3. Publisher отправляет `task_id` в RabbitMQ с приоритетом.
4. Worker читает сообщение из очереди.
5. Runner запускает задачу в отдельном процессе и обновляет статусы выполнения.

## Тестирование

Для сервиса можно использовать `pytest` для unit- и integration-тестов API, сервисного слоя и репозитория. Тесты лучше запускать отдельным шагом CI или отдельным контейнером, а не при старте FastAPI-приложения.

### Масштабирование

Приложение можно масштабировать горизонтально по двум направлениям:

- **API (`fastapi`)** — запуск нескольких экземпляров сервиса для обработки большего числа HTTP-запросов.
- **Worker (`worker`)** — запуск нескольких экземпляров воркеров для параллельной обработки задач из очереди RabbitMQ.

Дополнительно внутри одного worker параллелизм регулируется через переменную `MAX_CONCURRENT_PROCESSES`. Она ограничивает количество одновременно выполняемых дочерних процессов через `asyncio.Semaphore`.

Основные способы масштабирования:
- увеличить число экземпляров `worker`;
- увеличить `MAX_CONCURRENT_PROCESSES`;
- увеличить число экземпляров `fastapi`;
- при необходимости масштабировать PostgreSQL и RabbitMQ.

Важно учитывать, что реальная производительность зависит не только от числа воркеров, но и от доступных CPU/памяти, производительности базы данных и характеристик самих задач.

## P.S.

В рамках тестового задания решение намеренно упрощено:

- вместо Celery используется собственная реализация на RabbitMQ (`aio_pika`) и `multiprocessing`;
- не используется асинхронная версия SQLAlchemy — работа с БД построена на синхронных `Session` и `create_engine`;
- не реализован полноценный graceful shutdown worker’а при остановке pod/container;
- registry активных процессов хранится в памяти и не синхронизируется между несколькими worker-инстансами;
- не добавлены retry-механизмы, dead-letter queue и расширенный мониторинг.
